# SecAgent 技术报告

## 摘要

SecAgent 是构建在 Pi Agent Harness 之上的通用网络安全智能体 Profile。系统将安全任务处理建模为受授权范围、风险策略、工具能力和预算约束的状态空间搜索。它通过结构化任务理解、候选动作生成、计划与重规划、统一工具 Gateway、证据图、验证器、观察器和事件源 Session，形成“任务理解—决策—执行—证据—验证—重规划—报告”的闭环。

SecAgent 的自主性不是无边界地生成 Shell 命令，而是在已登记工具、显式 scope、策略、隔离、预算和审计的前提下自主选择下一步。系统把发现信号和确认结论分开，用证据关联、独立来源和验证状态支撑报告可信度。

## 1. 研究背景

网络安全任务具有目标异构、信息不完整、工具链复杂、结果互相矛盾和风险不对称等特点。纯规则编排难以覆盖多场景，纯对话 Agent 又容易出现目标和授权边界随上下文丢失、失败重复、Scanner finding 未经验证、子 Agent 扩权和进程重启无法恢复等问题。

本系统的技术路线是“语言模型负责理解和提出候选，确定性内核负责边界、排序、执行接口、证据和状态”。这样既利用模型处理非结构化信息的能力，又把关键安全判断落到可测试的代码路径。

## 2. 系统边界与创新点

### 2.1 系统边界

Pi 提供模型抽象、Agent Loop、AgentSession、扩展系统、CLI 和 Web 基础设施。SecAgent 提供网络安全特有的任务、scope、策略、工具、证据、报告和基准。外部扫描器由受控环境安装，仓库维护的是适配器、版本检查和调用策略，不重复实现扫描器。

### 2.2 主要技术特点

1. **双 Profile 兼容**：Coding 为默认，Sec 显式启用，模式写入 Session 且不可原地切换。
2. **事件源安全状态**：任务、scope、决策、证据、审计和预算均可重放。
3. **风险感知候选排序**：综合目标相关性、信息增益、置信度、风险、成本、新颖性和预算压力。
4. **能力级重规划**：失败不仅绑定到可执行文件，也绑定到能力族，防止换工具名掩盖策略停滞。
5. **证据图和确认闸门**：把观察、假设、验证和确认发现分离。
6. **结构化工具边界**：工具必须经过 registry、Gateway、scope/policy、前置条件和审计。
7. **可控自主策略**：autonomous 需要隔离和一次性授权，越界产生不可关闭的高危审计。
8. **可重放比赛基准**：在不调用付费模型和公网目标的条件下验证完整决策闭环。

## 3. 数据模型

### 3.1 SecurityTaskSpec

```text
id
goal
scenario
assets[]
constraints[]
successCriteria[]
declaredAuthorization[]
pendingConfirmations[]
createdAt
```

`pendingConfirmations` 明确列出输入中尚未得到授权或需要人工确认的事项。

### 3.2 SecurityState

```text
version / revision
task / goal / stage
policyMode / isolation / autonomousAuthorization / scope
evidence / evidenceGraph / hypotheses / rejectedHypotheses / findings
decisions / replans / observerSignals / delegations
budget / ctfProfile
```

所有状态通过 SecurityEvent 追加并由 reducer 重放。状态变更不会覆盖历史，因此可以解释某个决策当时看到了什么。

### 3.3 Decision 与 Audit

Decision 保存候选集合、选择动作、证据 ID、理由、预期结果、实际结果、状态、计划版本、尝试次数和预算快照。ToolAuditRecord 保存工具、调用 ID、风险、scope、policy 决策、审批、参数摘要、结果摘要、错误和告警。

系统不持久化模型的隐藏链式思考。对评审开放的是可复核的决策输入和结果，而不是未经必要处理的隐私或内部推理内容。

## 4. 自主搜索算法

### 4.1 候选生成

候选由当前任务和场景、阶段、显式 scope、本地输入资产、CTF 能力画像、已有证据和假设、过去结果以及 registry 工具能力共同生成。每个候选包含工具、描述、目标、能力、前置条件、预期证据、停止条件和估算成本。

### 4.2 评分

可将候选评分抽象为：

```text
utility(a) =
    goalRelevance(a)
  + informationGain(a)
  + confidence(a)
  - riskPenalty(a)
  - costPenalty(a)
  - noveltyPenalty(a)
  - budgetPenalty(a)
```

实际权重由实现和基准校准；公式用于解释变量关系，不应被当作未经版本绑定的正式比赛指标。高风险动作不能通过提高信息增益绕过 policy。

### 4.3 重规划

重规划触发器包括 decision failed、decision contradicted、decision stalled、repeated capability failure、verification contradicted/insufficient、budget pressure 和 Observer drift。Replanner 创建新 revision 和 replan 记录，保留上一决策 ID 和原因。成功候选不再重复；能力族在多次失败后被标记为耗尽或降权。

## 5. 工具执行 Gateway

```text
输入结构化 action
  → registry resolution
  → tool availability/version
  → deterministic input builder
  → precondition check
  → scope assessment
  → risk/policy decision
  → budget check
  → adapter execution
  → normalized result
  → audit + evidence
```

Gateway 是唯一的安全工具调用路径。未知工具采用保守风险下限；Shell 管道按其中最高风险工具评估。工具执行失败仍保留诊断和审计，不能让失败路径绕过约束。

## 6. Evidence Graph 与确认发现

证据节点保存 kind、summary、source、hash、confidence、decision IDs、target refs、agent role 和时间。边表示 supports、contradicts、derived-from、duplicates 或 verifies。

验证器只验证已有假设和证据关系，不凭空创建漏洞结论。Finding gate 要求关联有效 verification；没有足够证据时，结果保留为候选信号或 insufficient。

该设计解决“扫描器输出即漏洞”的问题：工具结果提供线索，独立来源和验证步骤提供结论依据，报告同时呈现支持和否定假设。

## 7. 专业 Agent 控制

六个专业 Agent 通过包资源加载：`sec-recon`、`sec-web`、`sec-analysis`、`sec-response`、`sec-vuln` 和 `sec-reverse`。子 Agent 使用任务信封，限制目标、工具白名单、最大轮次、时间、并发和预算。子 Agent 返回证据与状态，不拥有扩大 scope、启用 autonomous 或确认最终发现的权限。

## 8. Web 和 Session 恢复

Web 通过 Session Profile API 获取 `snapshot()`，通过结构化 `command` 变更状态，通过 SSE 接收 `profile_state`。这样 CLI 和 Web 看到同一事件源状态。

Session mode 写入 header，旧 Session 默认为 coding。Sec 进程重启后由 Runtime 重放任务和审计；Web SSE 断线后重连并获取最新 snapshot。长任务使用生产 Web 和外部进程监督，避免开发编译器重启中断活跃操作。

## 9. 安全策略形式化

对动作 `a`，Gateway 至少检查：

```text
authorized(a) =
  registered(a)
  ∧ preconditionsSatisfied(a)
  ∧ withinBudget(a)
  ∧ protectedPathsAllowed(a)
  ∧ policyAllows(a)
  ∧ scopeAllows(a)
```

在 strict/competition 中，`scopeAllows(a) = false` 直接阻断。autonomous 只有在 isolation 和 one-time authorization 已满足时，才把 scope 越界从应用层阻断转换为高危审计告警；OS/container 和受保护路径仍独立生效。

## 10. 受控基准与评估

| 基准 | 主要指标 |
| --- | --- |
| Web | scope、HTTP 观察、无重复成功动作、证据 |
| Pwn | artifact hash、ELF 画像、静态分析和预算 |
| Reverse | 只读分析、能力进阶、假设验证 |
| Forensics | 元数据/签名证据、来源和不自动执行 |
| Killchain | 多阶段覆盖、失败重规划、scope 和预算 |

基准评估同时检查安全不变量和能力覆盖。只满足“没有越界”但没有完成要求能力的 trace 不能取得完整能力分。

本次受控复核使用 Node.js `v22.23.2`，五个场景均通过。统一指标脚本输出任务理解成功率 100%、选中动作有效率 100%、受控工具调用成功率 100%、失败后重规划成功率 100%、证据验证覆盖率 100%；本次运行平均场景耗时 198ms，跨场景工具—能力组合重复比例为 50%。这些数据来自确定性受控执行器，不代表真实容器工具或在线模型的性能；正式提交时必须绑定冻结 commit、工具版本和归档日志。

## 11. 报告与可复现性

同一个 Session 可导出 Markdown 和 JSON。JSON 适合自动评估、归档和重放；Markdown 适合评审阅读。报告包含生成时间、任务、策略、scope、证据、验证、发现、决策、重规划、Observer、委派、预算和工具审计。

重放评估应固定 Git commit、package 版本、模型/Provider 配置标识（不含密钥）、tool registry 和工具镜像、fixture 输入哈希、初始 task/scope/policy/budget、executor 输出序列以及最终报告和审计哈希。可复现的目标是执行路径可追踪和状态可重建，不承诺非确定性模型在每个 token 上完全一致。

## 12. 性能、可靠性与局限

WSL Windows 挂载盘的性能瓶颈主要来自大量小文件的 `stat/read/write/delete`，不是 SecAgent 决策算法本身。Web 启动器将生成输出和 Webpack cache 转移到 `/tmp`，能降低编译产物 I/O；源码和依赖树仍应迁移到 ext4。

Web“断开”可能来自浏览器 SSE 网络、Web 进程重启、WSL 实例生命周期或部署监督器。客户端提供心跳、重连和轮询回退；持久化 Session 保证完成的安全记录可以恢复。生产演示必须使用生产构建、持久 Session 目录和外部进程监督。

模型输出仍可能错误，外部工具的结果质量受版本和环境影响，复杂协议和深度漏洞利用需要后续适配器，受控基准不等同于官方比赛成绩，在线部署指标需在最终环境测量。

当前容器验收尚未形成通过证据：`node:22-bookworm-slim` 的 Docker 构建阶段对 Debian 软件源/包体下载不稳定。镜像模板已增加构建网络、下载重试和可配置的 Debian/npm 镜像参数；网络恢复后需重新运行正式脚本，并将 `acceptance-summary.json` 和镜像 digest 纳入提交包。
