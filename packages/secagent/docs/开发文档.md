# SecAgent 开发文档

## 1. 适用范围

本文档面向需要构建、测试、扩展或维护 SecAgent 的开发人员。SecAgent 是 Pi monorepo 中的正式 workspace package，不是 `.pi` 目录中的临时脚本集合。安全内核和专业 Agent 定义的唯一源目录是 `packages/secagent/`。

## 2. 开发环境

### 2.1 版本要求

- Node.js `22.19.0` 或更高版本；
- npm 与仓库 lockfile 兼容的版本；
- Git；
- WSL 用户推荐 Linux ext4 文件系统；
- Docker/Compose 仅在容器和真实工具 smoke 测试时需要。

检查命令：

```bash
node --version
npm --version
git --version
```

### 2.2 安装依赖

```bash
npm install --ignore-scripts
```

Sec 模式本地演示所需的四个固定运行包：

```bash
SECAGENT_RUNTIME_DIR="$HOME/.pi/secagent-runtime"
npm init --yes --prefix "$SECAGENT_RUNTIME_DIR" >/dev/null
npm install --ignore-scripts --prefix "$SECAGENT_RUNTIME_DIR" --save-exact \
  pi-sandbox@0.6.3 \
  pi-mcp-adapter@2.23.0 \
  pi-subagents@0.50.0 \
  pi-trace-extension@0.1.14
export PI_SECAGENT_RUNTIME_DIR="$SECAGENT_RUNTIME_DIR"
```

运行包使用独立 npm prefix，避免其 peer 依赖参与根 workspace 的重新求解。容器构建使用 `/opt/secagent-runtime`；本地开发可使用 `$HOME/.pi/secagent-runtime`。安装过程使用 `--ignore-scripts`，并且只能从审查过的 npm registry、缓存或内部镜像获取固定版本。

`--no-save` 会使 `npm ls --depth=0` 把这些包显示为 `extraneous`，这是部署方式的预期结果。SecAgent 不会在 Session 启动时自动安装依赖。

## 3. 目录与职责

```text
packages/secagent/
├── agents/                  # 六个有界专业 Agent 定义
├── docs/                    # 架构、交付和比赛材料
├── fixtures/                # 一次性本地受控样本和 Web fixture
├── templates/               # Docker/Compose、sandbox、MCP 默认模板
├── src/
│   ├── agents/              # 控制面和专业 Agent 调度
│   ├── core/                # 状态、策略、scope、计划、证据、预算
│   ├── ctf/                 # CTF 能力画像
│   ├── intake/              # 任务与压缩包输入安全
│   ├── integrations/        # MCP 和 subagent 策略桥接
│   ├── report/              # Markdown/JSON 报告
│   ├── scenarios/           # 基准和受控执行器
│   └── tools/               # 工具 registry、Gateway 和 adapters
└── test/                    # 确定性回归和受控场景测试
```

## 4. 构建链

根构建必须先构建 SecAgent，再构建 Coding Agent：

```text
TUI → telemetry → AI → agent → session backend → protocol → client
  → server → secagent → coding-agent
```

常用命令：

```bash
npm run check
npm run build
npm run build --workspace=@earendil-works/pi-secagent
npm run build --workspace=@earendil-works/pi-coding-agent
npm run build --workspace=@agegr/pi-web
```

开发阶段按仓库规则运行 `npm run check`。正式演示前，从无 `dist` 的干净状态执行完整构建，并保存完整日志。Web UI 的 `next dev` 适合界面开发；长时间任务和录制演示使用生产构建。

## 5. Profile 接入机制

Coding Agent 通过通用 Profile 边界创建模式实例：

```text
agentMode
  → createAgentProfile()
  → createRuntime({ cwd, sessionManager })
  → additional resource paths
  → createExtensions()
  → AgentSession
```

SecAgent 的公开入口是 `createSecAgentProfile()`。Profile Runtime 只暴露 `snapshot()`、结构化 `command(command)` 和 `subscribe(listener)`。Web 不应直接解析 Session 内部条目，也不应自行维护一份安全状态。所有 scope、策略、隔离、授权和报告动作都必须经 Profile Runtime。

## 6. 添加安全能力的规则

### 6.1 新增工具适配器

1. 在 `src/tools/` 中定义工具元数据和适配器。
2. 明确 canonical name、alias、类别、能力、风险底线、scope 模式、前置和后置条件。
3. 实现可用性检查、版本诊断、结构化输入校验、确定性 argv 构造和结果归一化。
4. 在 registry 中登记，并通过 Gateway 执行。
5. 为成功、失败、超时、缺失、scope 越界和版本不兼容添加测试。
6. 不允许为了快速验证而调用任意 Shell；若工具不适配，返回结构化诊断。

适配器的输入应是结构化对象，例如 `{ target, path, timeoutMs }`，而不是来自模型的完整命令字符串。路径必须经过 cwd、常规文件、符号链接和受保护路径检查。

### 6.2 新增场景

1. 在 `src/scenarios/` 增加场景定义、能力覆盖和必要的受控执行器。
2. 定义成功条件、停止条件、预算和不可违反的安全不变量。
3. 同时加入正常路径、工具失败、结果矛盾和重规划测试。
4. 不使用公网目标；优先使用 faux executor 或 loopback/container fixture。
5. 在比赛文档中说明场景如何映射到证据和演示步骤。

### 6.3 新增专业 Agent

专业 Agent 是 Markdown 任务定义，不是独立的无限权限程序。定义应包含角色、输入输出格式、允许调用的工具类别、最大时间/轮次/并发/预算、scope 约束和证据引用格式。注册到 package 资源目录后由模式级资源路径发现；不要把相同文件复制回 `.pi/agents`。

## 7. 状态和事件

`SecurityState` 是由 Session 自定义事件重放得到的事件源状态，主要字段包括：

```text
task / goal / stage
policyMode / isolation / autonomousAuthorization / scope
evidence / evidenceGraph / hypotheses / findings
decisions / replans / observerSignals / delegations
budget / ctfProfile
```

新增事件时必须同时完成类型定义、reducer/replay 处理、快照与报告投影、恢复和分支测试、脱敏检查，以及 Web/API 是否需要暴露的评估。不要把模型隐藏推理过程写入 Session，只持久化可解释的输入证据、候选、选择原因、实际结果和审计摘要。

## 8. Web 开发

Web 通过 Profile API 使用安全运行时：

```text
GET  /api/agent/:id/profile       → profile snapshot
POST /api/agent/:id/profile       → structured profile command
SSE  /api/agent/:id/events        → profile_state updates
SSE  /api/agent/running/events    → running session snapshot
```

Sec 工作区只在 `agentMode === "sec"` 时渲染。新增 UI 文本必须同时进入英文和简体中文消息文件；模型、工具、诊断和发现的动态内容保持运行时原文，不通过匹配错误字符串强行翻译。

WSL 下 `/mnt/*` 的源文件读写仍然慢。启动器会把 `.next` 和开发 Webpack 缓存移到 `/tmp`，但最优方案仍是把仓库和 `node_modules` 放在 ext4。

## 9. 测试策略

```bash
npm run check
./test.sh
npm run test --workspace=@earendil-works/pi-secagent
```

定向测试应覆盖 scope、策略、任务边界、压缩包、Planner/Replanner、registry/Gateway、Evidence Graph、Session replay、delegation、benchmark、Profile 类型边界、Web API/SSE 和模式持久化。Coding Agent 测试使用 faux provider，不调用付费模型。真实工具测试只在 loopback、一次性容器或主办方明确授权环境运行。

## 10. 常见故障

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| autonomous 不可用 | 隔离未验证、运行包缺失或工具不齐 | 运行 `/sec-doctor`，补齐环境后重新建立授权 |
| `npm ls` 显示 extraneous | Sec 包用 `--no-save` 安装 | 只要版本正确即可；容器构建应记录锁定版本 |
| Web 首次请求很慢 | `/mnt/e` 9P 小文件访问和 Next 冷编译 | 使用 ext4 或生产构建；开发缓存由启动器迁到 `/tmp` |
| Web 显示断开 | 进程重启、WSL 实例重启或 SSE 网络中断 | 持久化 Session，使用生产模式/进程监督，客户端会重连并读取 snapshot |
| Web 加载旧代码 | `dist` 或 `.next` 过期 | 停止服务，按构建顺序重建；不要与 dev 同时运行生产构建 |
| 工具调用被阻断 | scope、风险、前置条件或预算不满足 | 查看审计和结构化诊断，不绕过 Gateway |

## 11. 代码审查清单

- [ ] 没有 `any`，没有动态 inline import，没有未经审计的 Shell 回退。
- [ ] 代码使用可擦除 TypeScript 语法，符合仓库 tsconfig。
- [ ] 所有外部依赖版本经过评审并锁定。
- [ ] 状态变更可重放，输出可脱敏，失败路径有审计。
- [ ] Web 与 CLI 共用 Runtime，不复制安全状态。
- [ ] 新能力有确定性测试和必要的真实 loopback smoke。
- [ ] 文档、测试与实现一致。
