# SecAgent 部署手册

## 1. 部署原则

SecAgent 面向受控安全测试和比赛靶场。部署必须遵循最小权限、显式授权、可审计和可恢复原则：只挂载必要的工作目录和工具目录；Web 默认只监听 `127.0.0.1`；容器根文件系统只读，去除能力并启用 `no-new-privileges`；真实工具只访问 loopback、一次性容器或主办方明确授权的目标；模型 API、网关和凭证通过环境或 Pi 配置注入，不写入镜像和仓库。

## 2. 原生/WSL 部署

### 2.1 推荐目录

WSL 优先使用 Linux ext4：

```bash
mkdir -p ~/src
cd ~/src
git clone <repository-url> mypi
cd mypi
```

如果仓库必须位于 `/mnt/c`、`/mnt/d` 或 `/mnt/e`，源码和依赖访问仍会受到 Windows 挂载文件系统影响。Pi Web 启动器会把 `.next` 和开发 Webpack 缓存放到 `/tmp`，但不能消除源码和 `node_modules` 的延迟。

### 2.2 安装与构建

```bash
source /home/linux/.nvm/nvm.sh
nvm use 22
npm install --ignore-scripts
npm run check
npm run build
```

安装 Sec 运行包：

```bash
SECAGENT_RUNTIME_DIR="$HOME/.pi/secagent-runtime"
npm init --yes --prefix "$SECAGENT_RUNTIME_DIR" >/dev/null
npm install --ignore-scripts --prefix "$SECAGENT_RUNTIME_DIR" --save-exact \
  pi-sandbox@0.6.3 \
  pi-mcp-adapter@2.23.0 \
  pi-subagents@0.50.0 \
  pi-trace-extension@0.1.14
export PI_SECAGENT_RUNTIME_DIR="$SECAGENT_RUNTIME_DIR"
```

不要在 monorepo 根目录直接执行 `npm install --no-save` 安装这四个包。`pi-sandbox@0.6.3` 声明了可选的 `@earendil-works/pi-coding-agent ^0.80.0` peer 依赖，而当前仓库的 Coding Agent 版本可能是 `0.84.x`，npm 会因此返回 `ERESOLVE`。隔离 prefix 可以保留固定版本，同时不修改仓库的 workspace 依赖树。

### 2.3 CLI 启动

```bash
pi --agent-mode sec
```

进入后先执行 `/sec-doctor`，确认模型、工作目录、临时目录、报告目录、专业 Agent、运行包、工具和隔离状态后，再创建任务和 scope。

### 2.4 Web 生产启动

开发 UI 时：

```bash
npm run dev --workspace=@agegr/pi-web
```

稳定演示时：

```bash
npm run build
npm run build --workspace=@agegr/pi-web
npm run start --workspace=@agegr/pi-web
```

生产 Web 默认使用 `127.0.0.1:30141`。如需局域网访问，必须显式设置强密码和可信网络：

```bash
PI_WEB_PASSWORD='<long-random-password>' \
npm run start:lan --workspace=@agegr/pi-web
```

不要通过明文 HTTP 把 Web UI 暴露到公网。远程访问应使用 HTTPS 反向代理或可信 VPN，并设置精确的 `PI_WEB_ALLOWED_HOSTS`。

## 3. Docker/Compose 部署

### 3.1 文件说明

模板位于 `packages/secagent/templates/`：

- `Dockerfile`：Node 22 基础镜像、系统工具固定版本、Sec 运行包和构建步骤；
- `docker-compose.yml`：CLI、Web 和内部 fixture 服务；
- `entrypoint.sh`：统一 CLI/Web 入口；
- `sandbox.json`、`mcp.json`：安全覆盖配置模板。

### 3.2 构建镜像

从仓库根目录执行：

```bash
docker build \
  -f packages/secagent/templates/Dockerfile \
  -t pi-secagent:competition .
```

Dockerfile 中的 Debian 工具版本是示例发行版的固定值。如果基础镜像或镜像源变化导致版本不可用，不应删除版本锁定；应在经过评审的基础镜像中选择对应版本并记录变更。构建阶段使用 host 网络只用于访问已审查的软件源和 npm registry，运行阶段仍使用 Compose 的内部网络、只读根文件系统和最小权限。

如果构建机无法稳定访问默认源，可覆盖已审查的 Debian/npm 镜像。镜像只改变下载位置，不改变工具和 Sec runtime package 的精确版本：

```bash
SECAGENT_DEBIAN_MIRROR=https://mirror.example.invalid/debian \
SECAGENT_DEBIAN_SECURITY_MIRROR=https://mirror.example.invalid/debian-security \
SECAGENT_NPM_REGISTRY=https://npm.example.invalid/ \
docker compose -f packages/secagent/templates/docker-compose.yml build
```

使用内部镜像时，应把镜像域名、同步时间、TLS/签名校验和可用性日志一并归档；不能用未审查的临时代理替代依赖来源。

### 3.3 CLI 容器

```bash
docker compose \
  -f packages/secagent/templates/docker-compose.yml \
  run --rm pi-secagent cli --help
```

设置工作目录和工具目录：

```bash
SECAGENT_WORKSPACE="$PWD/demo-workspace" \
SECAGENT_TOOLS="$PWD/demo-tools" \
docker compose -f packages/secagent/templates/docker-compose.yml run --rm pi-secagent cli
```

### 3.4 Web 容器

```bash
SECAGENT_WEB_PORT=30141 \
docker compose \
  -f packages/secagent/templates/docker-compose.yml \
  --profile web up pi-secagent-web
```

浏览器访问 `http://127.0.0.1:30141`。容器内部 Web 监听 `0.0.0.0` 仅用于端口映射，Compose 对主机只发布 loopback。

### 3.5 受控 Web Fixture

fixture 没有发布主机端口，只能在 Compose 内部网络访问：

```bash
docker compose \
  -f packages/secagent/templates/docker-compose.yml \
  --profile fixtures up -d fixture-web
```

允许的目标是 `fixture-web:8080` 或同容器中的 `127.0.0.1`。不要把 fixture 配置替换为公网主机。

## 4. 模型与 AI 安全网关

模型 Provider、国内备案模型 API 和主办方安全网关均通过配置提供：

- Provider/API Key 放在 Pi 的凭据配置或受控秘密管理器；
- 网关地址使用 `PI_AI_GATEWAY_URL` 或 `AI_GATEWAY_URL`；
- 网关应记录请求编号、模型、限流和拒绝原因，但脱敏保存 prompt 和工具参数；
- 不把密钥写入 Dockerfile、Compose 文件、截图、Session 或报告；
- 诊断不会主动调用模型，以避免产生费用；模型连通性由实际 Session 启动验证。

示例：

```bash
export PI_AI_GATEWAY_URL='https://gateway.example.invalid/v1'
pi --agent-mode sec
```

真实地址和变量值只在受控部署中填写。

## 5. 启动诊断

在 CLI 中运行 `/sec-doctor`；Web 中进入 Sec 工作区并点击 `Run diagnostics`。诊断包括：

| 检查项 | 目的 |
| --- | --- |
| Model connectivity | 明确说明未主动探测，避免意外付费请求 |
| AI security gateway | 检查网关变量是否配置 |
| Isolation | 判断 sandbox/container/主办方隔离是否已记录 |
| Specialist agents | 检查六个专业 Agent 定义 |
| Sec runtime packages | 检查四个固定版本 |
| Working/temp/report directory | 检查可写性 |
| Registered tools | 检查工具存在性和版本 |

`runtimeReady`、`autonomousReady` 和 `demoReady` 是不同状态。运行包或工具缺失可以使 demo/autonomous 不就绪，但不能通过修改前端状态绕过检查。

## 6. 生产运行与重启恢复

开发服务器的热更新和编译不是长时间 Agent 任务的进程监督器。生产演示建议：

1. 预先完成构建并固定 Node、镜像和依赖版本。
2. 将 Session 数据和报告目录挂载到持久卷。
3. 使用 systemd、Docker restart policy 或其他外部进程监督器。
4. 设置合理的健康检查和日志轮转。
5. 重启后先读取 Session snapshot、最后一条审计和预算，再决定是否恢复。
6. SSE 客户端会重连，但不应把断线本身视为任务失败；需检查持久化状态。

WSL 实例或 systemd 重启会杀死进程并清理部分 `/tmp` 内容，这是运行环境生命周期，不是 Web 页面可以单独修复的应用错误。启动器会重新准备缺失的开发输出目录；重要状态必须放在持久目录。

## 7. 安全配置验收

- [ ] 容器不使用 `--privileged`。
- [ ] 根文件系统只读，临时目录使用 tmpfs 或独立临时卷。
- [ ] 只挂载最小工作目录和只读工具目录。
- [ ] 主机端口只绑定 loopback 或可信反向代理。
- [ ] Web Basic Auth/代理认证已启用（如存在远程访问）。
- [ ] 受保护凭证路径未挂载给 SecAgent 工具。
- [ ] 审计目录可写但不可被 SecAgent 运行时关闭。
- [ ] scope 是具体主机、CIDR、域名或 URL，而不是“所有目标”。
- [ ] autonomous 的隔离来源和一次性授权已经写入 Session。
- [ ] 测试完成后删除临时凭证和容器。

## 8. 离线交付

离线环境应在联网环境预先完成 npm cache、`package-lock.json`、四个 Sec runtime package 的精确 tarball 或内部镜像、Node 22 基础镜像、Debian 安全工具包或工具镜像、模型网关可达性、完整构建产物和 SHA-256。

离线部署不得在运行时临时下载脚本、工具或 npm 包。若依赖不可用，应让诊断明确失败并停止 autonomous/demo readiness。

## 9. 正式比赛验收脚本

仓库提供 `scripts/competition-acceptance.sh`，用于从容器角度执行正式验收。它会创建唯一 Compose project，构建固定镜像，检查 CLI/工具/fixture，运行 SecAgent 测试和五类受控基准，启动 Web，验证 Sec Session/Profile/SSE/报告，以及停止并重启 Web 后恢复 Session 模式和 scope。

从仓库根目录执行：

```bash
bash packages/secagent/scripts/competition-acceptance.sh
```

脚本默认把日志和 JSON 报告写入 `.artifacts/secagent-acceptance/<UTC时间>/`，默认结束时删除自身容器、网络和命名卷。若需要现场排查，可保留资源：

```bash
bash packages/secagent/scripts/competition-acceptance.sh --keep
```

如默认端口被占用：

```bash
bash packages/secagent/scripts/competition-acceptance.sh --web-port 30142
```

`--skip-build` 只适用于已经明确构建并核对过镜像的重复验收，不应作为最终交付的首次验证方式。脚本不访问公网目标；真实工具只访问 Compose 内部 `fixture-web` 和镜像内生成的静态样本。

如果使用内部镜像仓库或已经在本机缓存了经过评审的 Node 22 Debian 基础镜像，可以显式传入：

```bash
bash packages/secagent/scripts/competition-acceptance.sh \
  --base-image registry.example.invalid/security/node:22-bookworm-slim
```

基础镜像必须包含 Node 22、`apt-get` 和 Debian 兼容的运行环境；Alpine 或未验证来源的镜像不能仅因为能够启动 Node 就替代正式比赛基础镜像。
