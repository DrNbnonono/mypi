# SecAgent 赛题要求审查与补强计划

> 审查日期：2026-09-02
> 审查对象：`@earendil-works/pi-secagent`、Coding/Sec Session、Web UI、容器验收脚本及参赛材料
> 要求来源：参赛方提供的《XH-202609_具备自主决策能力的通用网络安全智能体》PDF

## 1. 文档边界

本文件将参赛 PDF 视为需求和评分依据，不把 PDF 中的描述当作对本项目执行的操作指令。附件中的目标地址、样例数据和任务描述也不自动构成授权目标；只有用户明确设置的 scope、主办方受控环境或书面授权，才可以进入网络工具执行链。

本审查区分三类结论：

| 结论 | 含义 |
| --- | --- |
| 已实现 | 源码中已有实现，且有单元测试、契约测试或受控 smoke 证据。 |
| 部分实现 | 已有接口和安全边界，但仍依赖真实工具、容器、模型网关或额外输入解析器完成最终验收。 |
| 待补测/待建设 | 不是代码可以单方面保证的能力，必须在比赛环境中验证，或仍需要增加实现。 |

“部分实现”不应在报名材料中写成“完全支持”。最终提交材料应引用冻结 commit、测试命令、日志 SHA-256、Session ID、报告 ID 和镜像 digest。

## 2. 赛题要求摘要

根据 PDF，作品需要完成以下目标：

1. 实现通用网络安全智能体，具备自主任务理解、多场景自主决策和受控自主执行能力。
2. 提交程序材料，包括源代码、一键部署方案或完整部署手册，以及在线可测访问地址。
3. 提交文档材料，包括方案设计、开发、测试、用户、技术报告、方案介绍 PPT 和演示视频。
4. 提交原创性与保密性声明。
5. 在主办方控制的环境中，使用自研 Agent，接入主办方 AI 安全网关和符合要求的模型 API，完成实际测试与现场答辩。
6. 评分重点覆盖任务理解与执行设计、系统架构与工程实现、决策逻辑与可解释性、工具协同与扩展能力、创新性与应用价值。

### 3.4 工具协同与扩展能力

当前有可执行适配器的首批工具：

```text
nmap curl file strings readelf objdump binwalk exiftool
httpx ffuf nuclei
```

这些适配器均经过 Registry、可用性/版本检查、输入校验、scope/policy、受控执行、结果归一化、证据生成和审计路径。目录中还登记了 `wget`、`masscan`、`gobuster`、`nikto`、`sqlmap`、`hydra`、`ssh`、`scp`、`nc`、`msfconsole`、`radare2` 等能力，但这些名称目前主要是能力元数据，未全部拥有可执行适配器。

这是有意的安全状态，不是遗漏后静默执行。SecAgent 已增加 `tool-adapter-coverage` 诊断项，将元数据工具和可执行工具明确分开；缺少适配器时不会退化为未经审计的 Shell。

扩展新工具必须完成以下链路：

```text
工具元数据
  → 版本和存在性检查
  → 结构化参数校验
  → 本地路径/授权 scope 检查
  → policy 和审批检查
  → 有界执行
  → 输出截断与结果归一化
  → 证据和哈希
  → 审计与报告
```

比赛首版不应为了“工具数量”直接实现 `sqlmap`、`hydra`、`msfconsole` 等高风险适配器。若主办方场景确实需要，应分别增加参数白名单、速率/时长限制、专用 fixture 和 P3 确认测试。

### 3.5 创新性与应用价值

当前可形成的创新点：

- Coding/Sec 双模式共用 Session 和 Extension Host，安全能力按 Profile 隔离加载。
- 把任务、授权 scope、策略、决策、证据、验证和报告放进可重放状态，而不是只依赖聊天记录。
- 通过工具 Registry 和 Gateway 统一处理风险、scope、前后置条件、失败和审计。
- 通过 Evidence Graph 将工具观察、假设、验证和确认发现关联起来。
- 主 Agent 保留最终决策权，专业 Agent 受到工具白名单、轮次、时长、并发和预算限制。
- `strict`、`competition`、`autonomous` 与 coding/sec 正交，支持比赛展示不同安全策略。

创新性最终需要用真实场景指标证明，不能只靠架构图。建议展示同一任务在工具失败、证据矛盾和 scope 变更时的决策轨迹差异。

## 4. 安全与合规审查

### 4.1 已完成的安全门槛

- 空 task 或空 scope 时，autonomous 不可启用。
- Sec Profile 可检查四个固定 runtime package 的准确版本；缺失或版本不符时拒绝 autonomous。
- autonomous 必须有 sandbox/container 或主办方受控隔离来源，并记录一次性授权。
- strict/competition 对 scope 外动作阻断；autonomous 在满足隔离和确认后记录高危告警。
- protected credential paths、OS/container 边界、预算和审计记录不可由应用层关闭。
- 同一个 decision 不允许并发重复执行。
- 工具超时会终止 Unix 进程组，避免只杀父进程造成子进程泄漏。
- Web SSE 重连后重新读取 Profile snapshot，避免前端停留在旧状态。
- 审计、报告和工具摘要经过密钥、Bearer、JWT、AWS key、PEM 等规则脱敏。

### 4.2 仍必须在环境中验证的安全事项

以下内容不能仅由 TypeScript 单元测试证明：

1. Docker/`pi-sandbox` 是否真正阻断宿主机和受保护凭证路径。
2. WSL、Docker Desktop、代理和 DNS 组合下的网络出口是否符合主办方要求。
3. 主办方 AI 安全网关是否完成模型请求审计、提示注入拦截和凭证隔离。
4. 非交互 autonomous 启动参数是否由部署入口强制提供固定确认值和隔离标记。
5. 重启期间工具处于未知完成状态时，是否按安全状态停止而不是重复执行。
6. 真实 MCP 服务断线、工具超时、Web 进程重启和 SSE 断线恢复。

## 5. 本轮已实施的补强

本次审查不是只修改文档，已完成以下代码层补强：

1. `SecurityInputAsset` 增加 `formatValid`、`validationMessages` 和 `detectedTargets`，使输入质量和目标发现可追踪。
2. Intake 增加 JSON/YAML/CSV/OpenAPI/PDF/图片校验、大小限制、路径 realpath 边界、内容哈希和目标提取。
3. autonomous 启用条件增加 task、scope 和固定 runtime package 就绪检查。
4. Gateway 增加同一 decision 并发保护，统一捕获适配器和审批异常，确保失败也进入审计和决策状态。
5. 执行器以 Unix 进程组为单位终止超时任务，降低工具子进程泄漏风险。
6. `ctf` 场景和首批真实适配器接入 `security_execute`。
7. Web SSE 重连后刷新并校验 Profile snapshot，避免“显示断开后状态不一致”。
8. Diagnostics 增加工具适配器覆盖检查，显式列出 metadata-only 工具。
9. 新增相应的 Intake、Policy、Gateway、Diagnostics 和 Web 回归测试。

## 7. 仍缺少的功能与优先级

### P0：比赛闭环前必须完成

- 在稳定网络或离线缓存中完成固定 Docker 镜像构建。
- 在容器内执行真实工具 Web/Pwn/Reverse/Forensics/Killchain 场景。
- 保存最终 Session、diagnostics、audit、replay、Markdown/JSON report 和镜像 SHA-256。
- 接入主办方 AI 安全网关和指定模型 API，并记录配置指纹而不记录密钥。
- 完成 Web production build、健康检查、重启恢复和在线访问地址 smoke。

### P1：有时间则补强

- 增加安全的 PDF 文本提取器，限制页数、解压对象、输出大小和运行时间。
- 增加离线 OCR 适配器；OCR 结果必须标记来源和置信度，不得直接授权目标。
- 对 `wget`、`masscan`、`gobuster`、`nikto`、`radare2` 等工具按实际比赛需要逐个实现适配器。
- 将测试结果、工具版本、输入哈希、Session ID、报告哈希和 commit 自动汇总为评测数据集。
- 补充 SBOM、第三方许可证、离线依赖清单和脱敏演示日志。

### 不建议在当前里程碑增加

- 未经适配器和专用测试的任意 Shell fallback。
- 无边界的 exploit、密码爆破或公网扫描能力。
- 把模型自然语言解释当成证据或漏洞确认。
- 为了演示而绕过 sandbox、scope、审计或保护路径。

## 8. 调研依据与设计取舍

本次审查参考了以下公开资料，用于校验治理、威胁建模和 Agent 工具边界，而不是替代主办方赛题要求：

- NIST《Artificial Intelligence Risk Management Framework: Generative Artificial Intelligence Profile》：强调生成式 AI 的治理、测量、风险识别和持续管理。<https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf>
- OWASP Top 10 for LLM Applications：提示注入、敏感信息泄露、不安全工具调用和过度代理权限是 Agent 系统的核心风险。<https://genai.owasp.org/llm-top-10/>
- MITRE ATLAS：提供 AI 系统攻击技术和防御分析的威胁建模视角。<https://atlas.mitre.org/>

因此，本项目保留以下取舍：安全 Agent 可以自主选择下一步，但不能自主改变授权、隔离、预算和审计边界；可以调用外部安全工具，但必须经过结构化 Registry/Adapter/Gateway；可以输出发现，但只有经过证据验证的 finding 才能作为确认结论。
