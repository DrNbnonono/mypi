# SecAgent 现场演示脚本

## 1. 演示目标

本脚本用完全受控的 loopback/container 场景，展示：

```text
任务理解 → 授权 scope → 环境诊断 → 候选动作
→ 计划与执行 → 工具审计 → 证据验证
→ 注入失败 → 自动重规划 → Markdown/JSON 报告
```

演示只使用本机 `127.0.0.1`、Compose 内部 `fixture-web:8080` 或主办方提供的明确授权靶场。正式录制前，将占位符替换为最终环境实际值。

## 2. 演示准备

### 2.1 环境

- Node.js `22.19.0+`；
- 四个固定版本的 Sec runtime package；
- Nmap、Curl、file、binutils、binwalk、ExifTool 等工具已通过诊断；
- Docker/Compose fixture 已启动（如使用）；
- 模型已配置，或使用主办方 AI 网关；
- Web 生产构建已完成；
- 空白工作目录和可写报告目录；
- 浏览器语言先设置为中文，随后展示英文切换。

### 2.2 启动

```bash
docker compose -f packages/secagent/templates/docker-compose.yml \
  --profile fixtures up -d fixture-web

npm run build
npm run build --workspace=@agegr/pi-web
npm run start --workspace=@agegr/pi-web
```

如果从容器启动：

```bash
docker compose -f packages/secagent/templates/docker-compose.yml \
  --profile web up pi-secagent-web
```

### 2.3 录制前检查

- [ ] 目标仅为 fixture 或授权地址。
- [ ] 浏览器地址、模型 key、Cookie 和真实路径不会进入录屏。
- [ ] 诊断没有把公网地址列入 scope。
- [ ] 录像中的版本和提交号与提交材料一致。
- [ ] 准备一次受控工具失败或 controlled harness 的 `injectFailure=true`。
- [ ] 准备指标文件 `controlled-acceptance.json`，并确认其中包含 Git commit、Node 版本和统一指标。
- [ ] 若容器正式验收尚未通过，现场不得声称真实工具镜像已完成比赛验收；应明确演示使用的是受控 fixture。

## 3. 正常路径（约 6 分钟）

### 步骤 1：创建 Sec Session

操作：在 Web 新建会话，选择 `Sec`。

解说：

> 这里选择的是 Agent Profile，不是安全策略。Coding 仍是默认模式，Sec 必须显式创建。Session 会持久化为 Sec，恢复时不会偷偷切回 Coding。

展示 Session 列表中的 `Sec` 徽标和安全工作区。

### 步骤 2：运行诊断

操作：点击 `Run diagnostics` 或在 CLI 执行 `/sec-doctor`。

解说：

> 诊断检查运行包、专业 Agent、工具版本、工作目录、临时目录、报告目录和隔离状态。模型连通性不主动探测，避免诊断本身产生付费请求。

展示 `runtimeReady`、`autonomousReady`、`demoReady` 和工具状态。

### 步骤 3：任务理解

输入示例：

```text
请对本次比赛提供的 loopback Web fixture 做只读服务识别和有限 HTTP 验证。
成功条件：记录可复现的 HTTP 证据、工具版本、决策理由和报告。
禁止访问 fixture 以外的地址，不执行状态变更操作。
```

操作：运行 `security_intake`。

解说：

> Intake 把自然语言拆成目标、场景、约束、成功条件和待确认项。即使任务文字中出现其他 IP，也不会自动变成授权目标。

### 步骤 4：设置 scope 和策略

操作：设置目标 `fixture-web:8080` 或 `127.0.0.1`，填写授权来源为本地一次性 Compose fixture 或最终授权编号，策略选择 `competition`，隔离选择 sandbox/container 来源。

解说：

> Scope 是执行边界，策略决定风险确认方式。competition 允许受控的 P2 动作，但 P3 仍需确认，越界仍会被阻断。

### 步骤 5：生成候选和计划

操作：运行 `security_candidates`、`security_plan` 或让 Agent 通过工具调用。

解说：

> Planner 同时考虑目标相关性、信息增益、置信度、风险、成本、重复动作和剩余预算。系统会记录候选集合和选择原因，而不是只显示最后一条命令。

展示候选列表、decision、expected result 和 budget snapshot。

### 步骤 6：执行工具

操作：执行登记的 Nmap/Curl/Web adapter。

解说：

> 工具调用经过 registry、输入校验、scope、policy、预算和 Gateway。模型不能直接把任意 Shell 字符串交给执行器。

展示工具版本、策略判定、目标、结果摘要和审计时间线。

### 步骤 7：证据与观察

操作：查看 Evidence、Hypotheses、Decision 和 Observer。

解说：

> 观察结果不是确认漏洞。证据会关联来源、哈希、置信度和决策；验证器根据证据图确认或否定假设，Observer 判断是否停滞或漂移。

## 4. 失败与重规划路径（约 4 分钟）

### 步骤 8：注入受控失败

操作：对第二个候选注入一次工具超时、工具退出错误或 controlled harness 的 `injectFailure=true`。

解说：

> 这里的失败是预先设计的受控故障，不是访问未授权目标。系统将错误、工具版本、输入摘要和 decision ID 写入审计。

### 步骤 9：观察重规划

操作：运行 `security_autonomous` 的 `step` 或 `run`，查看新 revision。

解说：

> 失败不会简单地重复同一动作。Replanner 识别失败触发器，降低已失败能力的优先级，选择满足前置条件的替代候选，并记录上一决策、重规划原因和新的预期结果。

展示 `replans`、`observerSignals`、新旧 decision、能力失败记录和预算使用变化。

### 步骤 10：展示安全边界

操作：尝试使用一个不在 scope 的目标，仅使用受控测试输入，不发出真实请求。

解说：

> strict/competition 下该动作被阻断，并产生审计记录。如果演示 autonomous，必须先展示已验证的隔离和一次性授权；越界会产生高危告警，但不会关闭 OS/container、凭证保护、预算和审计。

## 5. 报告导出（约 2 分钟）

操作：分别下载 Markdown 和 JSON 报告。

解说：

> 报告包含任务、scope、策略、隔离、证据图、验证、假设、决策、重规划、观察器、专业 Agent、预算和工具审计。默认脱敏，便于提交和复盘。

展示 Markdown 的 Decision Trace 和 Tool Audit Timeline，以及 JSON 中的 state/report 字段、verification ID 和 evidence ID。

## 6. Coding 模式兼容展示（可选）

操作：新建 Coding Session。

解说：

> Coding 是默认模式，不加载 SecAgent 安全面板、专业 Agent 和 Sec 运行包。两个模式共享稳定的 AgentSession，但安全状态只在 Sec Profile 中启用。

## 7. 收尾台词

> 本次演示证明的不是一次扫描命令，而是一条可复现的安全决策链：系统理解任务，确认授权，选择受约束的工具，记录证据，处理失败并重新规划，最后生成可审计报告。所有目标均在受控范围内，附件和模型输出都不能绕过授权边界。

## 8. 演示故障处理

| 故障 | 现场处理 |
| --- | --- |
| Web 首次加载慢 | 说明 WSL 挂载盘冷编译，使用生产构建或提前预热 |
| 页面显示断开 | 检查进程，刷新 Session，展示持久 snapshot 和审计，不重复未知完成动作 |
| 工具缺失 | 展示结构化诊断，改用已登记 fixture 工具或 faux harness |
| 模型超时 | 保留状态，展示失败审计和重规划；不要编造结果 |
| 语言未切换 | 刷新页面并检查 locale；动态工具输出保持原语言是预期行为 |
| autonomous 未就绪 | 不绕过；改用 strict/competition 完成受控演示，并解释前置条件 |

## 9. 演示证据归档

演示结束后保存录屏 SHA-256、Git commit、镜像 digest（如已构建）、Session ID、报告哈希、诊断 JSON、工具版本清单、统一指标 JSON、脱敏服务日志、目标/授权记录和容器销毁记录。建议使用以下稳定文件名：

```text
evidence/
├── environment.txt
├── controlled-acceptance.json
├── competition-metrics.json
├── security-boundary.log
├── session-report.json
├── report.md
└── screenshots/
```

其中 `competition-metrics.json` 应包含指标定义、分母、Git commit、输入哈希和运行时间；没有真实容器结果时，必须把 `containerAcceptance` 标为 `FAIL` 或 `PENDING`。
