# SecAgent 比赛提交材料清单

本文档用于组织参赛作品的最终提交包。它把题目要求中的三类材料拆成可核验的文件，并明确哪些内容已经存在于仓库、哪些内容需要在最终比赛环境中补充。文档本身是 Markdown 材料，可在提交前转换为 PDF 或纳入压缩包。

## 一、题目要求与提交结构

题目要求的作品至少包括以下三部分：

1. **程序材料**：智能体编译前源代码、一键部署方案或完整部署手册、在线可测访问地址。
2. **文档材料**：方案设计文档、开发文档、测试文档、用户手册、技术报告、方案介绍 PPT、阐述演示视频等。
3. **声明函**：参赛方案原创性及保密性声明。

## 二、源代码交付检查

- [ ] 源代码可以从一个全新的目录解压并按部署手册构建。
- [ ] 不包含 API Key、OAuth token、Cookie、私钥、`.env`、个人会话、浏览器缓存或真实目标数据。
- [ ] `.pi` 中只保留项目配置和部署覆盖，不把安全内核复制为第二份实现。
- [ ] `packages/secagent/agents/`、`src/`、`templates/`、`test/` 和文档均包含在源代码包中。
- [ ] `package-lock.json`、SecAgent 运行包版本和工具镜像版本已固定并记录。
- [ ] 记录最终 Git commit、Node.js 版本、操作系统、容器基础镜像和构建时间。
- [ ] 对源代码压缩包和镜像导出文件生成 SHA-256 校验值。

## 三、在线可测地址模板

仓库不应虚构在线地址。部署完成后复制以下模板为 `online-test/access-url.md` 并填写：

```markdown
# 在线可测地址

- 访问地址：需填写
- 协议：需填写 HTTPS / 受控内网 HTTP
- 可用时间：需填写开始时间至结束时间，使用带时区的 ISO 8601
- 认证方式：需填写临时账号、单点登录或主办方网关
- 测试范围：仅允许访问主办方明确提供的靶场或题目目标
- 联系人：需填写姓名、邮箱或比赛平台账号
- 限制：禁止公网扫描、禁止上传真实凭证、禁止超出授权范围的测试
- 健康检查：GET / 返回 200；Session API、Sec Profile API 和报告下载已验证
- 版本：需填写 Git commit、容器镜像摘要和 SecAgent 版本
```

在线地址必须经过访问控制、日志保留和最小权限配置。演示账户不应复用开发人员个人凭证；测试结束后应立即失效。

## 四、文档质量检查

每份正式文档至少应包含适用版本和日期、目标读者、前置条件、可执行步骤或可验证结论、已知限制和失败处理、代码/测试交叉引用，以及敏感信息审查结果。

## 五、最终验收门槛

### 程序与部署

- [ ] `npm run check` 通过。
- [ ] SecAgent 定向测试通过。
- [ ] Coding/Sec 模式持久化、恢复、模式冲突测试通过。
- [ ] Web 首页、Session API、新建 Sec Session、Profile API、SSE、报告下载通过。
- [ ] 从无 `dist` 状态完成构建，且生产 Web 可以启动。
- [ ] 容器以非 root、只读根文件系统、最小挂载和 loopback 端口运行。
- [ ] autonomous 在没有隔离和一次性授权时被拒绝。
- [ ] 只对 loopback、一次性容器或主办方明确授权目标进行真实工具测试。

### 文档与媒体

- [ ] PPT 中的每项能力都能指向代码、测试或演示证据。
- [ ] 视频展示任务理解、计划、执行、证据、重规划、审计和报告，而不是只展示模型回答。
- [ ] 测试报告区分确定性 CI、真实本地工具和比赛环境结果。
- [ ] 技术报告不把候选发现写成未经验证的漏洞结论。
- [ ] 声明函已由所有需要的作者或负责人审阅。
- [ ] 在线地址和所有临时账号已登记并经过脱敏审核。

### 6.4 提交前封包流程

1. 冻结提交版本：记录 Git commit、版本号、Node.js 版本、操作系统、容器基础镜像和工具版本。
2. 在干净副本中执行源代码包检查、密钥扫描和依赖完整性检查。
3. 按[部署手册](部署手册.md)执行构建、启动和容器验收；将完整验收目录复制到 `evidence/container-acceptance/`。
4. 执行 Web 演示：创建 Sec Session、设置 scope、查看 diagnostics、运行受控场景、查看审计/决策、下载 Markdown 和 JSON 报告。
5. 对每项能力建立“能力—代码路径—测试编号—证据文件—演示时间点”映射，补入技术报告和 PPT。
6. 清理 API Key、Cookie、Session 文件、真实目标、内部域名和个人路径；复核截图、日志、视频字幕和 PPT 备注页。
7. 生成提交包和 SHA-256，使用另一台环境或另一名成员按用户手册进行一次复核。
8. 由负责人确认在线地址、账号有效期、数据保留策略、应急联系人和声明函签署状态。

## 七、风险、限制与未完成项

以下项目必须在最终提交前逐项关闭，或在提交说明中明确披露影响、替代方案和补测时间。它们不是可以通过“功能代码已存在”自动豁免的事项。

| 项目 | 当前影响 | 临时措施 | 关闭条件 |
| --- | --- | --- | --- |
| 容器镜像构建/完整验收 | 未形成可宣称的容器通过证据 | 保留每次失败日志；网络恢复后重新执行正式脚本 | `acceptance-summary.json` 为通过，且镜像 digest 已记录 |
| 在线可测地址 | 评委无法从外部访问 | 在提交包中提供本地容器复现方式 | 受控 URL、认证、时间窗和联系人已验证 |
| WSL `/mnt/*` 性能 | 开发冷启动和小文件访问可能很慢 | 使用 ext4、生产 Web 构建和持久化 Session | 记录 ext4 与挂载盘耗时，演示环境满足响应要求 |
| Web 进程/SSE 重启 | 可能出现短暂断线 | 使用生产进程监督；重连后读取持久化 snapshot | 重启回归通过，未重复执行未确认动作 |
| 外部模型/网关 | 网络或配额可能影响在线演示 | 使用主办方网关或已审查的离线/faux 路径 | 记录连通性、超时、限流和备用方案 |
| 安全工具可用性 | 工具缺失时场景能力不完整 | 使用固定镜像和启动诊断，不回退到任意 Shell | 工具版本清单与诊断均通过 |
| 声明函与媒体 | 材料形式不完整或泄露敏感信息 | 先使用模板和隔离靶场录制 | 签字文件、正式 PPT 和视频完成脱敏复核 |
