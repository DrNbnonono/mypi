### 1.3 SecAgent 产品代码修复（均含测试，测试基线 93 passed / 0 failed；全仓 tsgo --noEmit 通过）

1. **bash 放行** — `packages/secagent/src/extension-scope-guard.ts`
   - 原状：Sec 模式无条件禁用 bash（"direct shell execution is disabled in Sec mode"），任何 policyMode 都一样 → 模型被迫走有缺陷的 `security_execute`。
   - 修复：仅 `strict` 模式禁用；competition/autonomous 放行，仍受 protected-path、scope、风险分级（P3 在 competition 仍需确认）约束。
   - 测试：`test/scope-guard.test.ts` 重写断言 + 新增 competition/autonomous 放行用例。

2. **curl 适配器解析 command 字符串** — `packages/secagent/src/tools/curl.ts`
   - 原状：适配器只读结构化字段（`target/method/headers/data`），模型传的 `command` 字符串被**静默忽略** → 所有 POST 实际以裸 GET 发出（证据：gateway 回显 argv 只剩 `--silent --show-error --write-out <url>`）。
   - 修复：新增 `parseCurlCommand()`：引号感知 tokenizer；支持 `-X/--request`、`-H/--header`、`-d/--data/--data-raw/--data-ascii/--json`、`--url`、`-L/--location`、`-I/--head`、`-A/-e`、短旗标簇（`-sS`、`-skL`）、忽略无副作用旗标（`-k/-i/-v/--compressed` 等）；不支持的 flag **抛错**（precondition 失败回显原因），`@file` 与 proxy 类 flag 明确拒绝。
   - 测试：`test/tools-standard.test.ts` 新增原始命令解析 + 不支持旗标报错用例。

3. **scope 伪 host 误判** — `packages/secagent/src/core/scope.ts`
   - 原状：`DOMAIN_PATTERN` 对整个输入做正则扫描，URL 路径内部的 `19px.png`、`security.txt`、`00.md` 被提取为"站外域名"→ 合法请求被 scope guard 拦截。
   - 修复：URL 匹配区域整体 scrub 后再做 IP/域名提取；域名候选若前导字符为 `/`（路径段）跳过；bash 场景仅提取 URL/IP 候选（自由文本中的文件名不再误判）。
   - 测试：`test/scope-policy.test.ts` 新增伪 host 回归用例。

## 2. 测评设计与采集方法

- **任务书**（各轮一致，示例见 run6）：授权声明 + 目标 + 作业流（SQLi 登录 → `/api/Challenges` 榜单 → 按难度逐题、读源码、服务端触发判分）+ 时间盒约束（单 bash ≤30s、每题 ≤10 次调用、禁 `find /`）+ 硬性范围约束（仅 127.0.0.1:3000）。
- **启动方式**：`pi --agent-mode sec --mode json [-p|--continue] "任务书"`，后台执行；competition 策略通过**预置会话条目**注入（`secagent:event` 自定义条目 `{type:"policy_changed",mode:"competition",...}`，运行时 `replaySecurityState` 重放生效）。
- **采集**：stdout JSON 事件流全量落盘——`thinking_delta/thinking_end`（完整思维链）、`message_end`（逐响应 usage：input/output/cacheRead/cost/reasoning）、`tool_execution_start/end`（含 security_execute 的 argv 回显）。会话原始 JSONL 另存 `~/.pi/agent/sessions/<encoded-cwd>/`。
- **判分复核**：操作员以 SQLi 登录获取 admin token，每轮前后拉取 `/api/Challenges`（116 行）做差集；关键发现独立复现验证。
- **解析器**：`sec-parse.mjs`（本仓库外临时脚本）从事件流提取 turns/工具调用/token/费用/思维链/最终答复/工具日志。

## 3. 关键根因发现（本次测评最有价值的产出）

### 3.1 curl 适配器丢参（产品缺陷，已修复）

第一轮全量测评中，agent 对 `/rest/user/login` 的 SQLi 探测全部返回 500 "Unexpected path"，并据此得出"v17 路由未注册、SQLi 不可达"的**错误结论**。操作员同 payload 直接 POST 得到 200 + admin token，证明结论错误。根因链：

1. 模型传 `security_execute {tool:"curl", input:{command:"curl -sS -X POST -H ... -d ... <url>"}}`；
2. 适配器只读结构化字段，`command` 被静默忽略，重建 argv 为 `["--silent","--show-error","--write-out",...]`；
3. 裸 GET 打在仅注册 POST 的路由上 → 500；
4. 模型未比对"请求命令 vs 实际 argv"，将错误观测合理化为版本路由变更叙事。

方法论教训：**工具回显的实际执行参数必须与请求参数做 diff 校验**；跨通道抽样复测（bash 直连对照）可提早暴露此类问题。

### 3.2 decide→execute 前置摩擦（易用性缺陷）

run0 中 44 次 `security_execute` 有 21 次（48%）被 `Decision … does not exist` 拒绝——模型先使用自拟可读 id，被拒后才换用 `security_decide` 返回的 UUID。修复建议：execute 原子化"声明+执行"，或 schema/提示词显式约定。

### 3.3 safetyMode：剩余题停滞的真正根因

run5 后 agent 停滞在 94/116，剩余题读源码均"无解"。逐层排查发现：v20 的 `getChallengeEnablementStatus`（build/utils.js）在检测到 Docker 环境时按 `challenge.disabledEnv` 禁用全部 danger-zone 挑战（`challenges.safetyMode: auto`），路由代码退化为消毒分支（如 trackOrder 的 id 被 `[^\w-]+` 清洗）。处理：

```bash
wsl docker commit <cid> juice-shop-state:v1        # 保留镜像层（注意：DB 状态未能保留）
wsl docker run -d --name juice-shop -p 127.0.0.1:3000:3000 \
  -e 'NODE_CONFIG={"challenges":{"safetyMode":"disabled"}}' juice-shop-state:v1
```

启用后同一 payload 立即可判分。**代价**：v20 每次容器启动都会重置挑战状态（94→10），且 commit 未能保住进度，因此需要 run6 全量重解。另注：v20 容器为 distroless（无 sh/node），排查需 `docker cp` 提取编译产物。

### 3.4 挑战 key 与名称映射

容器内挑战 key（代码 solveIf 使用的稳定标识）与 yml 展示名可被构建期重排（如 `rceChallenge` 显示名不是 "RCE"）。**一切判分分析必须以 key 为准、以容器内编译产物为准**，GitHub 源码仅作参考。

## 6. 未解 6 题逐项归因

## 7. 改进建议（按投入产出排序）

1. **security_execute 增加请求/实际 argv diff 自检**（防 §3.1 类静默失真，一行高亮即可）。
2. **decisionId 工作流简化**：execute 允许原子"声明+执行"，或 schema 示例强制 UUID 来源。
3. **为 bash 工具增加默认超时**（本测评两轮被 `find /` 类命令挂起，靠操作员杀进程解锁）。
4. usernameXss 的 pug 渲染路径需一次浏览器实测，确认服务端判分在真实渲染下的行为。
5. web3 三题如需纳入演示，准备 anvil（Sepolia fork）+ 预置钱包的 compose profile。
