# SecAgent 测试报告

## 1. 报告目的

本文档定义 SecAgent 参赛版本的测试方法、测试分层、验收标准和结果记录格式。仓库已有确定性测试和 Web smoke；最终比赛镜像还必须补充实际工具、容器和在线地址的测试日志。

报告中的结果必须绑定 Git commit、Node/npm/操作系统版本、依赖 lockfile、Sec runtime package 版本、容器镜像 digest（如适用）、测试命令、时间、退出码、原始日志路径以及 Session/report ID。

## 2. 测试原则

1. 默认测试不调用付费模型、不访问公网目标。
2. faux provider 和 controlled executor 用于确定性 CI。
3. 真实工具只访问 loopback、一次性容器或主办方书面授权目标。
4. 正常路径和失败路径同等重要，失败必须验证审计和重规划。
5. 测试发现与安全结论分离，不能用字符串匹配代替验证。
6. 任何被跳过的测试必须记录原因和补测计划。

## 3. 测试分层

```text
静态检查/类型检查
        ↓
SecAgent 单元与核心状态测试
        ↓
Coding/Sec Session 与 Profile 集成测试
        ↓
Web API、SSE 和 UI 契约测试
        ↓
受控五场景端到端测试
        ↓
真实工具 loopback/container smoke
        ↓
最终容器和在线演示 smoke
```

### 3.1 静态与构建检查

```bash
npm run check
npm run build
npm run build --workspace=@agegr/pi-web
```

`npm run check` 检查格式、精确依赖、TypeScript 导入、Coding Agent shrinkwrap/install-lock、TypeScript 类型和浏览器 smoke。构建前应确认没有开发 Web 进程占用 `.next`。

说明：`npm run build` 是根仓库构建，当前根脚本不包含 Web UI；Web 生产构建须单独执行 `npm run build --workspace=@agegr/pi-web`。正式报告必须记录两条命令的独立退出码，不能用 `npm run check` 替代构建验收。

## 5. 受控场景验收

| 场景 | 成功证据 | 失败注入 |
| --- | --- | --- |
| Web | HTTP 可观测性、scope、adapter audit | 首个工具失败后改变能力路径 |
| Pwn | ELF 哈希、缓解措施和静态证据 | 分析工具失败后保留 artifact 并换工具 |
| Reverse | strings/readelf/objdump 证据链 | 重复策略被抑制 |
| Forensics | 元数据/签名证据和来源 | 不自动提取、不执行样本 |
| Killchain | 多阶段能力覆盖和重规划 | 中间阶段矛盾/失败触发重规划 |

确定性 harness 只替换外部执行器，仍运行真实的 Candidate Generator、Planner、Gateway、policy/scope、adapter、Evidence Graph、Verifier、Observer 和报告路径。

## 6. Web 与重启回归

### 6.1 冷启动

记录 `/`、`/api/sessions`、创建 Coding Session、创建 Sec Session、Profile、diagnostics 和 report download 的冷/热耗时。WSL `/mnt/*` 上的冷启动可能很慢，不应只以开发服务器冷请求时间判断 Agent 算法性能；应同时记录 ext4、`/mnt/*`、dev 和 production 对比。

### 6.2 重启恢复

1. 创建 Sec Session 并写入任务、scope、decision 和 audit。
2. 请求完成后停止 Web 进程。
3. 重新启动相同版本。
4. 恢复 Session，确认 `agentMode=sec`。
5. 确认 task、scope、policy、evidence、decision、audit 和 budget 未丢失。
6. 确认前端 SSE 重新建立，且没有重复执行未确认完成的动作。

## 10. 容器化验收执行

正式验收入口为：

```bash
bash packages/secagent/scripts/competition-acceptance.sh
```

该脚本的输出目录包含阶段日志、工具输出、受控五场景 JSON、Web API 响应、SSE 初始事件、重启前后 Profile 和最终 `acceptance-summary.json`。最终测试报告应把该目录整体归档，并记录镜像 digest、Git commit 和运行时间。

验收脚本包含以下门槛：

1. Compose 配置可解析，镜像能够从固定依赖构建。
2. Sec CLI 的 `--help`、`--version` 可用。
3. Nmap/Curl/静态分析/取证工具在容器中可执行。
4. 内部 fixture 健康，Nmap 和 Curl 只能访问内部网络。
5. Web/Pwn/Reverse/Forensics/Killchain 受控基准全部通过。
6. Killchain 注入一次失败后仍通过，并产生失败决策和 replanning。
7. Web 可创建 `agentMode=sec` Session，初始 autonomous 被拒绝。
8. Profile、报告和 running SSE 可访问。
9. Web 停止/重启后 Session mode 和 scope 恢复。
10. 脚本默认清理自身 Compose 资源，保留日志和报告。

| R-04 | 在线地址和主办方网关 | 当前仓库不提供真实服务地址 | 程序材料不完整 | 填写 URL、有效期、认证、联系人和健康检查证据 |
| R-05 | 真实工具与模型依赖 | 受环境、版本、网络和配额影响 | faux 结果不能替代比赛环境结果 | 区分确定性、loopback 和在线结果，记录缺失能力 |
| R-06 | 演示与声明材料 | 需制作正式 PPT、视频并签署声明 | 文档材料/声明函不完整 | 完成脱敏、签字和材料清单复核 |

任何风险关闭前，不得把“代码路径存在”“单元测试通过”表述为“完整比赛验收通过”。报告结论应明确区分：已通过、失败、跳过、待补测和不适用。
